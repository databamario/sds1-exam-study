## Running it locally

```bash

pip install -r requirements.txt

```

## The gates

Everything below must pass before a commit. Check the exit code, not the output.

```bash
python tools/check_all.py      # build + all gates, in the right order
```

which runs, in order:

```bash
python tools/build_bank.py         # rebuild data/questions.json
python tools/validate.py           # schema, counts, keys, R coverage, option format
python tools/verify_r.py           # run every R snippet
python tools/verify_numbers.py     # check every number a question asserts
python tools/verify_second_pages.py # a second cited page must earn its place
python tools/test_scoring.py       # grading regression tests vs the official table
python tools/test_answer_format.py # the MC format rules
python tools/test_progress.py      # the browser-stored progress layer
```

`verify_citations.py` is deliberately **not** one of them: it needs the lecture PDFs and produces
a ranking, not a verdict, so it cannot pass or fail.

R is not on PATH here. It lives at `C:\Program Files\R\R-4.6.1\bin\Rscript.exe`, and both R gates
find it on their own.

### What each gate is actually for

Two of these exist because the first version of the R gate was decorative: it turned each snippet
into a string literal instead of running it, so invalid R reported PASS. Both are now proven to
fail â€” each was run against the bank as it stood before the check was added, and both reported the
real problems.

- **`verify_r.py`** really executes every snippet. Because most snippets are fragments lifted out
  of the lecturer's session, it prepends a fixture holding stand-ins for the objects the slides
  already define. That proves the code *runs and calls the right API*; it says nothing about
  values, because the values are synthetic.
- **`verify_numbers.py`** covers the values. Each check names a number the question claims,
  requires that claim to still be in the question text, and then either recomputes it in R or
  looks it up in the source slide. Editing a number in the bank breaks the check instead of
  silently passing it.
- **`validate.py`** also fails if an MC question loses its correct option, if an explanation
  contradicts its own answer key, if a written answer runs long, if a question refers to the
  course rather than to the statistics, or if a referenced figure file is missing.
- **`verify_second_pages.py`** checks the second side of a two-page citation. Some questions are
  answered by a pair of slides - one states the problem, the other carries the formula or the
  numbers - and when only one page could be cited the only fix was to delete real course content.
  `source` therefore carries `slide` (the page everything else reads) and, when a question needs
  more, `slides`, the full set, always starting with `slide`. This gate requires every extra page
  to supply at least one term the primary page leaves unexplained.

  It is deliberately a low bar. One incidental word passes it, and that is a known false pass:
  `L1-MC-019` cited a page supplying only the word `lists` and did not need it. A threshold would
  not fix this - `L3-WA-004`'s extra page supplies one word too, but it is the only word that
  carries the answer, because the decisive term is too common for the scorer to count. So the
  gate *prints what each extra page supplied* and leaves the judgement to a reader. Passing is
  not evidence the page was needed.

A gate that can only fail is noise, and a gate that cannot fail is worse, so every rule is
checked twice: once that it catches the violation it exists for, and once that a correct bank
passes it.

## Answer-format rules

Position is a free guess for anyone who notices the pattern, and the shape of that free guess
depends on the question.

With **five options and two correct**, the giveaway is a *pair*: a student who always ticks (a)
and (b) is right on every question whose key happens to be {a,b}. With **four options and one
correct**, it is a single position. `validate.py` fails when one pair holds more than 20% of the
five-option questions, or one position more than 35% of the single-correct four-option ones.

Both limits come from the sample size, not from whatever the bank happens to do. This replaced an
earlier check that watched the position of the single *false* option instead: that was a different
game, and it only looked at questions with more than one correct option, so the single-correct ones
went entirely unchecked.

Current shape: **137** five-option questions with exactly two correct, **20** four-option questions
with one, and nothing with more than two correct anywhere. The most common key pair holds 13.2% of
the five-option questions, against an even spread of 13.6% across the ten possible pairs.

When you add a question, spread the key rather than letting it fall where it falls, and say *what*
is wrong in the explanation rather than naming a letter. An explanation that says "(d) is false"
silently becomes a lie the moment the options are reordered. Where an explanation does name a
letter, `validate.py` checks the name against the key.

`tools/rebalance_pairs.py` fixes a lopsided key distribution by rotating options. It refuses to
touch any question that refers to a position ("the first plot") or a letter ("so (c) is false"),
since rotating those would contradict their own text, and after writing it rebuilds the bank and
checks that every question kept its options, its true options, its stem and its explanation.

## The citation review

`validate.py` proves every citation names a real lecture file and a page inside it — all 243 pass.
That is not the same as being the *right* page, which is why **every one of them has now been read
by hand against the slide it cites**: all 243, the 30 figure questions and the 213 from the nine
lectures. **43 of them were wrong** and are fixed. `REVIEW_LOG.md` records each one with the reason.

`tools/show_citation.py` prints a question beside the text of the slide it cites, which is the only
thing that has found these. `validate.py` reports every one of them as perfectly formed.

### How the shortlist was chosen, and where that stopped working

The reading began in score bands with `tools/verify_citations.py`: 67% in the worst band, 28% in
the next, then 0% in the band after that, then 38% on a probe of the band below, then 27% and 22%
on the two batches that followed. The zero in the middle was a gap in the signal rather than the
end of it — the bands on either side both gave errors, so it did not stop there.

The score then stopped discriminating altogether. Measured on a band of 30, the eight defective
questions scored **0.129** on average and the 22 clean ones **0.118**: the defective ones ranked
slightly *worse*, and reversing the order would have changed nothing. From that point the bank was
read by hand in lecture order, not by score.

Three classes of error came out of the reading. They are worth separating because from inside the
tool they look identical — in all three the key words are simply absent from the cited page:

1. **A claim the lecture never makes.** `L1-MC-018` keyed `factor(x, levels = ...)`; `levels =`
   appears nowhere in Lecture 1. `L2-MC-018` keyed `summary()`; it appears nowhere in Lecture 2.
   `L3-WA-008` compared a histogram with a bar plot, which Lecture 3 does not teach. `L9-WA-008`
   claimed regression was deferred to SDS2; `SDS2` appears nowhere in Lecture 9.
2. **A real slide the question does not cite.** 26 questions now cite two or three pages, added
   with `also=[...]` and checked by the gate described above. `L4-MC-009` needs p.32, p.33 and
   p.34 together: the definition, the confidence level, and the coverage.
3. **A rubric grading something the keyed answer does not say.** `L9-WA-003` and `L9-WA-006` each
   graded a clause their own answer never contained, so a student answering perfectly would have
   lost those points for not saying more than the key.

### Read the key from the source, never from a dump

Eight questions in this review looked wrong only because a rendered snapshot was misread rather
than because the question was defective. Two of those were reported as tool bugs and were not tool
bugs: `show_citation.py` marks every keyed option correctly.

The last of the eight was a viewer written minutes earlier, for this review, specifically to avoid
that failure. So the rule is not "trust the tool" or "distrust the tool" — it is that a dump and a
question must never disagree in the bank's favour:

```python
# wrong: judge the answer key from rendered output
python tools/show_citation.py L7-MC-009     # I read KEY> on one line and missed the other

# right: read the key from the source the bank is built from
grep -A6 '"L7-MC-009"' tools/bank/l7.py    # -> ["a", "c"]
```

`data/questions.json` is equally authoritative, and `check_all.py` fails if it differs from what
`tools/bank/` produces, so either is a valid thing to check a verdict against.

```bash
python tools/verify_citations.py                  # the 25 worst-matched citations
python tools/verify_citations.py --figures        # which slide each figure's questions cite
python tools/verify_citations.py --id L7-MC-016   # one question beside its slide
python tools/verify_citations.py --proximity      # citations whose content is on the next page
python tools/show_citation.py L7-MC-016           # the same, with the code block shown
python tools/verify_second_pages.py               # each extra cited page, and what it supplied
```

The dominant cause is structural: a question inherits its lecture's citation wholesale even when
the content belongs elsewhere, so one wrong page silently mis-cites every question sharing it.
Three questions about random variables sat in Lecture 4 citing a slide about drawing cards.

The commonest single cause is narrower and mechanically avoidable: the slide is split across two
PDF pages, and the cited one holds the statement of the problem while the *next* one holds the
code, the formula or the worked numbers. Forty-one questions sit on the first page of such a pair.

The page number is an **index into the PDF**, not the number printed in the slide footer. Reading
it as the footer scores 26% against the slides; reading it as an index scores 78%. There is no
systematic offset to correct in bulk, which is why every page was read by hand.

## Topics not to write questions about

Both are named in the syllabus and are **not** in the bank, because the lectures do not teach them:
linear regression (deferred to SDS2 three separate times â€” L1 p.13, L8 p.22, and Lecture 9 never
returns to it) and Bayes' theorem (appears on no slide; only the OpenIntro 3.5 reading assigned
to Lecture 4 puts it within reach). The mock exam's help-page question has the same problem: no
slide covers the anatomy of a help page, though L2 p.41 does cover packages and `library()`.

If a lecturer announces any of these will be tested, this app will not have covered it. Adding
questions for them would mean anchoring them to material the course does not contain.

## Sounds

The four interface sounds are WAV files in `assets/sfx/`, generated by `tools/make_sfx.py` from one
source recording, and embedded into `src/sfx_data.py` by `tools/build_sfx.py`. They are played by
`celebrate.flush()`, which is called once at the end of `app.py`.

`src/sfx_data.py` is generated. Never edit it by hand â€” edit the WAVs and re-run
`python tools/build_sfx.py`. `check_all.py` fails if it is stale relative to the WAVs.

Do not reintroduce a `static/` directory or `server.enableStaticServing`. It was tried, and it
does not serve the files; see the postmortem in [DEPLOY.md](DEPLOY.md) for what happened and why.

## Regenerating the sounds

```bash
python tools/make_sfx.py     # rewrites assets/sfx/
python tools/build_sfx.py    # rewrites src/sfx_data.py
```

`make_sfx.py` cuts the long tail off the source, downmixes to mono, resamples to 16 kHz and sets
the peak, then derives the other three sounds by shifting its pitch, so they belong to one family.

## Two validation layers, before any push

`tools/check_all.py` runs the data side — schema, R, numbers, scoring, progress, second pages.
None of those scripts ever launch Streamlit. That is fine for the *content*, but it leaves the
*runtime* unguarded: a `TypeError` from a bad kwarg on `components.html(...)` would pass every
gate and crash the deployed app an hour later when someone opens the page. The same is true for
any wrong seed value that the JS widget then refuses to render. Two layers exist so this stops
being the discovery path.

### Layer 1 — `tools/test_app_smoke.py` (in the suite, automatic)

`streamlit.testing.v1.AppTest` boots `app.py` in-process, lets us peek at session state and the
widgets, and reruns without a browser. The file is run as the eighth gate by `check_all.py` and
covers:

- `test_app_runs` — boots the script twice (idle, then with a sound queued) and asserts no
  exception from `celebrate.flush()` or anywhere else at module level. This is the gate that
  caught the `key=html()` regression from `7cb8327`.
- `test_wa_streak_refresh_after_chip` — pins the WA streak recomputation inside `_wa_body`.
  Before the fix the cached `streak` argument was passed in before the chip click updated `done`,
  which suppressed the confetti for WA entirely.
- `test_mock_exam_seed_within_widget_bounds` — navigates into Mock exam with a fresh session so
  `setdefault("exam_seed", _new_seed())` actually calls the seed source. With the old
  `random.getrandbits(64)` this raised `StreamlitJSNumberBoundsError` on more than half of the
  first opens.
- `test_new_seed_is_within_st_widget_bounds` — direct unit-level check that `_new_seed()` in
  `practice.py` and `mock_exam.py` returns values in `[0, 2**31)`.
- `test_mc_streak_refreshes_after_check` — pins the MC streak recomputation after the
  Check answer rerun.

To run it on its own: `python tools/test_app_smoke.py`.

A change that wants to add AppTest coverage should follow the same shape: drive the page once,
assert the visible side-effect, and keep the test self-contained.

### Layer 2 — Chromium click-through (manual, before risky pushes)

For anything that touches `celebrate.py`, `ui.py` or `app.py`, the eight gates do not see what
the browser sees. The procedure is:

1. From the repo root, start a clean server on a port that nothing else uses:

   ```bash
   python -m streamlit run app.py \
     --server.port 8512 \
     --server.headless true \
     --browser.gatherUsageStats false \
     --server.fileWatcherType none \
     > streamlit.log 2> streamlit.err &
   ```

2. Drive Chromium with `chrome-devtools` MCP:
   - `new_page url=http://localhost:8512`, then for each in-scope page
     (Home → Study MC → Study WA → Mock exam → Answer key → Progress → R coverage), `take_snapshot`
     and `list_console_messages` to catch any red box.
   - At least one click on a checkbox (MC), one tick on a WA chip and a full Mock-exam start to
     exercise `celebrate.flush()` with a sound queued.
   - Capture a screenshot if anything looks off; the snapshot diff catches most things first.

3. Kill the server when done:

   ```bash
   pkill -f 'streamlit run app.py' || true
   ```

   On Windows PowerShell: `Get-Process python | Where-Object { $_.CommandLine -match 'streamlit run' } | Stop-Process -Force`.

When this layer caught a regression locally, the change does not get pushed.
